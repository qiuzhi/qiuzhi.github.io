# AI Agent 随记


试用了近来很火的龙虾，最终选择了马。
我的 Hermes 使用记录始于一个很普通的问题：「你是谁？」紧接着，我问了广州当天的天气。两个月后，它已经不只是回答问题，而是在 Telegram 里查资料、改配置、跑脚本、调 Docker 服务、生成 Word 文档、调用高德地图、维护任务与笔记，还要定期检查自己的技能体系有没有越长越乱。
回头看，这段过程真正变化的不是问题越来越复杂，而是我逐渐把 AI 的工作标准从「给个答案」改成了「把事情做完，并留下下一次还能复用的能力」。

## 一 从问答开始先让它真的能做事

最早的使用方式和大多数人差不多：问身份、查天气、了解一个工具、比较几个方案。第一次查广州实时天气时，Hermes 甚至还没有拿到 `web\_search`。这件小事后来成了整个使用历程的缩影。

当时没有继续接受「我不能联网」这个结果，而是一路追到 Telegram 工具集、`config.yaml`、Tavily API Key 和 Gateway 进程环境。配置写进文件不等于运行中的进程已经读到；重启 Gateway 不等于旧 Session 会自动获得新工具。直到新会话里真实调用了 `web\_search`，实时天气才算查成功。

这次经历让我很早就形成了一条判断标准：

&gt; AI 说「可以」不算完成，配置文件里写着「启用」也不算完成；只有实际跑过并拿到结果，才算完成。

之后，无论是检查系统状态、修改脚本、调用接口还是生成文件，我都会继续追问：改到了哪个文件？运行的是哪套环境？进程有没有加载？结果验证了吗？

也正是在这个阶段，Hermes 从聊天机器人变成了能碰真实系统的工具。它开始读取日志、检查目录、执行命令、定位配置，回答也从「理论上应该」逐渐转向「现场实际是什么」。

## 二 从能执行到能排障

工具一多，真正有价值的部分很快从「会调用」变成了「出问题时能找到根因」。

### 1 Hindsight 缺失依赖

接入 Hindsight 长期记忆时，Hermes 的配置允许启用 `memory.provider: hindsight`，但官方 Docker 镜像里没有 `hindsight-client`。表面现象只是日志反复出现模块缺失，继续往下查才发现：

* 配置入口存在；
* 插件运行时确实会导入 Python Client；
* `pyproject.toml`、锁文件和 Dockerfile 又没有把它装进镜像；
* 手工装进 `/opt/hermes/.venv` 虽然能修，但容器重建后会丢失。

最后没有简单归因成「少装了一个包」，而是把它判断为镜像组成与功能声明没有对齐。查到上游已有同类 Issue 后，也没有重复提单，而是整理 Docker 复现证据，准备补充到现有讨论里。

这类排障让我开始要求完整证据链：日志只能说明症状，配置、源码、依赖和进程状态拼在一起，才能说明根因。

### 2 Docker 路径混淆

当然，AI 也会犯很具体的错。一次 AfterGateway 定时脚本整理中，Hermes 按裸机习惯把 `\~/.hermes/scripts` 当成固定目录，还为此复制出一份运行脚本。我指出当前是 Docker 安装，真正的持久化 Home 是 `/opt/data`，它才重新检查 `HERMES\_HOME`、进程环境和 Cron 配置，把多出来的目录删掉，只保留唯一有效脚本。

这件事并不光彩，但很经典。它推动了一条长期规则落地：

```text
/opt/hermes：程序与虚拟环境，不当作持久目录
/opt/data：Hermes Home、配置与运行数据
/opt/data/workspace：按项目存放工作文件
```

从那以后，环境事实不能靠默认印象，必须以当前容器现场为准。对 AI 来说，承认「刚才套错模板了」比继续圆回来有用得多。

## 三 从一次任务到长期自动化

当即时操作稳定后，我开始把重复需求交给 Cron。第一批任务里，广州中石化油价日报最有代表性。

最初的要求只是「每天整理广州本地油价」。任务跑起来后，很快发现现价并不是最有价值的信息，下一次国内成品油调价窗口才是。因此报告结构被改成：先报窗口和是否官宣，再报当前零售价，最后补最近一次正式调整。

随后又经历了几轮真实使用中的修正：

* Cron 时间从 UTC 误解纠正为 `Asia/Shanghai`；
* 报告从一大段搜索结果，改成可以扫一眼看完的分层简报；
* 链接从裸 URL 改为可点击文字；
* 相同事实不再前后重复；
* 不是看见数字就加粗，而是只突出真正影响判断的状态和价格。

这让我意识到，自动化任务最难的不是「按时执行」，而是长期输出仍然有用。一个每天准时制造信息垃圾的 Cron，只是更勤快的噪音源。

### 1 Agent World 酒馆任务的三次改造

AfterGateway 酒馆互动则把自动化又往前推了一步。最早由 Agent 全程自主执行喝酒、留言、发图和点赞；之后改成脚本准备数据、Agent 负责生成内容和提交；最后又改成 `no\_agent=true` 的纯脚本任务，只在需要创作留言时调用一次模型。

改造不是为了追求「脚本比 Agent 高级」，而是前两版真实出现了旧 Session 复用、重复留言、重复点赞和业务状态不一致。流程里真正需要创造力的只有留言，剩下都是确定性 API 操作，交给脚本反而更稳。

最终形成的原则很朴素：

&gt; 需要判断和表达的部分交给模型，需要幂等、状态和重试的部分交给脚本。

这也是后来周期自动化优先脚本化的来源。Agent 不应该为了证明自己自主，把本可确定执行的流程变成概率事件。

## 四 从通用助手到专用工具箱

随着任务类型增加，我开始为重复场景建立 Skill。New API 管理接口是最早的一批：先读官方文档，整理鉴权、渠道、模型、令牌、日志和统计接口，再把凭据单独放进权限收紧的密钥文件。之后在对应 Topic 里问「今天日志有没有异常」，Hermes 不再从头研究接口，而是直接拉日志、检查失败流和慢请求。

后面陆续形成了更多专用能力：

* GPT Image 兼容接口调用；
* Telegram 通知集成排障；
* 自托管应用部署；
* Docker 自动更新与 Watchtower 白名单；
* 可疑链接检查；
* 图片文字与型号识别；
* New API 渠道亲和、限流和故障转移排障；
* Hugo 博文整理与 Markdown 文件投递。

Skill 的价值不是让我少写几句提示词，而是把已经验证过的做法固定下来：什么时候触发、先查什么、哪些坑不要再踩、最后怎样验证。

不过，技能越多也会产生新问题。到七月，技能列表已经膨胀到上百个，开始出现重复触发、边界重叠和把历史战报塞进长期技能的情况。于是又做了一次对抗性审查：合并重复的 Plan 和代理面板技能，收紧图片生成链路，拆分过大的技能，明确 Docker、Gateway、Provider、记忆与 Wiki 各自的边界。

这是一个有点反直觉的阶段：早期总觉得能力越多越好，后来才发现，Agent 的成熟也包括知道哪些东西不该同时加载。

## 五 接入生活而不只管理服务器

如果一直停留在 Docker、日志和 API，这套系统顶多算一个运维助手。真正让我感觉使用方式变了，是它开始接入日常事务。

### 1 地图、任务和笔记

高德地图 MCP 接入后，位置不再只是聊天里的一段地址。Hermes 可以查周边、比较距离、规划驾车和公交路线，结合天气安排出行，并生成能直接唤起高德地图 App 的链接。

滴答清单 MCP 让某个 Telegram Topic 变成随手任务入口：一句自然语言可以落成当天任务、提醒或清单。Joplin 则承接更长的笔记、资料整理和知识沉淀。聊天入口没有变，但背后已经连接到地图、任务系统和笔记库。

这时 AI 的角色不再只是「告诉我怎么做」，而是把信息送到它最终应该存在的地方。

### 2 从手写纸到暑假学习计划

儿子的暑假学习计划是另一类典型任务。起点只是一张带涂改的手写纸，后面又陆续加入学校指引、课程安排、旅游日期和家长修订要求。最终产出不只是一次文字整理，而是多周每日待办、英语学习指引和综合计划等一组 Word 文档。

这项任务也把「人和 AI 谁说了算」讲得很清楚：AI 负责识别、分类、排期、生成和校验；家长手工修订后的文件则成为唯一权威版本。内容一致的 Archive 没必要保留，旧 AI 初稿也不能和权威文件混在一起。

AI 可以很勤快，但不应该和人的最终决定争夺版本控制权。

### 3 把 TXT 小说送进 Kavita

自部署小说阅读是更完整的一次小型项目。最初只是询问有没有 Docker 部署的离线阅读应用，最后落地成：

```text
中文 TXT
  → 自动识别章节与编码
  → 生成 EPUB
  → 每本书独立目录
  → Kavita 扫描入库
  → 手机通过 PWA 阅读
```

后来发现大文件还没上传完成就被扫描，生成了残缺 EPUB，于是转换器增加文件稳定窗口：大小和修改时间连续十分钟不变才开始转换，发布前再检查一次；如果期间文件继续变化，就删除临时 EPUB，原 TXT 留在原位等待下一轮。

这一改动很能说明后期的使用习惯：不只关心「能不能转换」，还关心传输中断、原子发布、重复扫描和失败恢复。一个能跑的脚本，与一个可以长期放着不管的服务，中间差的正是这些边界条件。

## 六 让记忆也接受治理

刚接入 Hindsight 时，我期待的是「以后不用反复解释」。随着记忆增多，问题很快变成另一种：什么值得长期保留，什么只是某次任务的残留？

于是记忆逐渐被分成几层：

```text
User Profile：稳定的个人偏好、身份与长期资产
Memory：少量高价值环境事实与约定
Skill：可复用的流程、坑点与验证方法
LLM Wiki：更长的知识页和可检索细节
Session History：临时进度、战报和当时的讨论
Workspace：脚本、日志、运行状态与交付文件
```

长期细节后来迁入 LLM Wiki，Memory 只保留索引入口；Hindsight 也不再追求「全都记住」，而是定期复核、提炼少量精选事实，再让散碎来源软失效。

这一步看起来不像增加能力，反而像在主动遗忘。但真正可用的长期记忆不是仓库越堆越满，而是下次出现相似任务时，能准确找回那几条真正改变做法的信息。

同样的治理也延伸到了 Skill：不保存某次游戏战报，不把临时路径当成永久规则，不让一段已经过期的事故复盘每次都进入上下文。Skill 应该是一张清楚的路由表，而不是背在 Agent 身上的杂物间。

## 七 我现在怎样理解 AI Agent

这两个月里，有查天气、修容器、做油价日报、玩 Agent World、整理学习计划、生成博客、管理书库，也有不少不那么体面的时刻：工具没加载、时区算错、路径套错、旧 Session 被复用、文档说法和本机代码不一致。

这些经历最后没有把我带向「让 AI 获得更多权限就行」，反而形成了更克制的使用方式：

1. **先查现场，不凭默认印象猜环境。**
2. **能执行就不要只给步骤，执行后必须验证。**
3. **确定性流程脚本化，判断与表达才交给模型。**
4. **人的修订是权威版本，AI 负责辅助而不是夺权。**
5. **长期能力写进 Skill，长期事实放进记忆或 Wiki，临时进度留在 Session。**
6. **自动化必须持续产生价值，否则宁愿静默。**
7. **能力需要治理，能删、能合并、能收窄边界，同样是进化。**

所以，我现在不太在意它像不像一个「全能 AI」。我更看重的是：面对一个真实问题，它能不能找到正确的工具，理解当前环境，做完该做的动作，承认中途的错误，验证最后的结果，并把可复用的部分留给下一次。

从「你是谁」到「检查一下你自己的技能体系有没有冲突」，中间并没有发生某个神奇的跃迁。只是一次次把答案推向执行，把执行推向自动化，再把自动化推向治理。

最后得到的也不只是一个更聪明的聊天机器人，而是一套仍在迭代、但已经真正参与日常工作的个人系统。
